给友链页加上随机排序：每次刷新，朋友们的顺序都不一样

发表于 2026-11-26|更新于2026-11-26|Hexo教程
|字数总计:8319|阅读时长:31分钟|阅读量:—

本站的友人帐（/links/）有一个小细节：同一个访客连着刷新五次，会看到五种不同的顺序。排在前面的不是固定那几位，每个朋友都有机会出现在第一屏。

这篇教程就是把这个细节拆开讲清楚。它没有装任何插件，也没有多一个 npm 包，全部代码就是一个 95 行的 source/js/flink-shuffle.js，再加模板里一个 data-shuffle 属性。

核心思路只有一句话：先把同一组里的卡片节点收集起来，洗一遍牌，再按新顺序塞回原来的容器。 标题、描述、卡片内容都不动，只动位置。

所有代码都会在文中完整给出，复制就能用。你不需要懂构建脚本，只要能新建一个 .js 文件、在页面里加一行 <script> 就行。

第 0 步：先想清楚“随机”要发生在哪一层

很多人第一反应是写一个 Hexo 生成器插件，在 hexo generate 的时候把 link.yml 打乱。这个思路能做出来，但效果不对：

方案 什么时候打乱 访客刷新会变吗 代价
构建时（Hexo 脚本 / 标签插件） 每次 hexo generate 不会，只有重新部署才换一次顺序 要写 Node 脚本，改一次数据就要重新生成
运行时（浏览器 JavaScript） 每次页面加载 会 一个静态 js 文件 + 一行 <script>

Hexo 是静态站生成器，它把 source/_data/link.yml 渲染成一份固定的 public/links/index.html。这份 HTML 一旦生成，顺序就焊死了；你在服务器上把它原样发给一万个访客，看到的都是同一套排列。想让顺序变，只能每次部署重新生成，或者——让浏览器在页面加载后自己洗牌。本站选的是后者。

还有三个新手常见的误解，先在这里说清楚：

  1. 随机排序不影响 SEO。 所有友链卡片依然在 HTML 里，爬虫抓到的链接一个不少，只是它们的位置不同。
  2. “随机”不等于“每次一定不同”。 两张卡片时，有 50% 的概率洗完还是原来的顺序；十张卡片时才几乎不可能重复。看到一次没变，不代表代码没跑。
  3. 不需要后端、不需要数据库。 洗牌用的是 Math.random()，纯浏览器行为。

第 4 步：逐段拆解这份源码

下面按代码顺序讲。你可以一边看文章，一边对着第 3 节的代码。

4.1 为什么整个文件包在 (function () { ... })() 里

这叫立即执行函数（IIFE）。它做了两件事：

  • 里面声明的 shuffle、pickCards、shuffleGroup、run 都变成局部变量，不会挂到 window 上，也不会和别的脚本重名；
  • 'use strict' 让一些“写错了但不报错”的代码直接抛错，比如给未声明的变量赋值。

新手最容易踩的坑是：把函数写在最外层，结果和主题里另一个叫 run 的函数撞名，后加载的把前面的覆盖掉，页面就莫名其妙不动了。

4.2 shuffle()：为什么不能写 sort(() => Math.random() - 0.5)

这是 Fisher-Yates 洗牌，也叫“从后往前抽牌”：

  1. 从最后一张开始，在 0 ~ i 这个范围里随机抽一个位置 j；
  2. 把第 i 张和第 j 张交换；
  3. i 往前走一位，重复，直到只剩第一张。

因为每一步的 j 都落在“还没确定的部分”里，每种排列出现的概率完全相同。这正是“每个人都有机会排到最前”的数学保证。

网上流传的另一种写法：

看着更短，但它给比较函数返回随机数，浏览器内部排序算法怎么比较、比较多少次都不确定，结果是有偏的——某些卡片更容易落在前面。友链这种讲究“公平”的场景，别用这一句。

另外注意 return arr 是多余的（数组是引用，改的就是原数组），保留只是让调用处读起来更像“返回了一个新数组”，无害。

4.3 pickCards()：只认直接子元素

三个要点：

  1. 用 children 而不是 querySelectorAll。 children 只包含直接子元素。假如哪天卡片里又嵌了一层 .site-card（比如推荐位），querySelectorAll 会把它也抓出来，然后 appendChild 把它搬到组末尾，看起来就像“卡片跑到别的分组去了”。
  2. nodeType !== 1 是为了跳过文本节点。 Pug 渲染时卡片之间会有换行和空格，它们也是 children 的成员，但不带 classList，不跳过后面的判断会报错。
  3. 三种 class 是三个时代的产物。 .site-card 对应截图卡，.flink-list-item 对应 Butterfly 风格的横排卡（也就是 flink 标签渲染出来的那种），.flink-list-card 是旧版弹性格子，模板已经不再渲染，留着判断只是让老站点升级后不至于失效。

如果你换的主题一个都不匹配，第 8 节会讲怎么改。

4.4 shuffleGroup()：分拣、洗牌、插回

这是核心函数，逻辑可以拆成四步：

第一步：卡片少于两张就直接退出。 一张卡洗牌等于没洗，零张卡更没意义。这个判断还能防止后面的 Math.random() 白算。

第二步：把卡片分成“有 pin”和“没 pin”两堆。 getAttribute 读到的永远是字符串，所以要 parseInt(..., 10) 转成十进制数字。空字符串转出来是 NaN，0 和负数会被 pos > 0 挡掉——这两种都当作“没写 pin”，走随机。

第三步（最常见的情况）：一个 pin 都没有，纯随机。 洗完牌直接按数组顺序 appendChild 回去。这里没有任何“先清空容器”的操作，因为：

appendChild 对已经在文档里的节点来说，是移动而不是复制。

第一张被移动时，它会从原位置被摘下来放到末尾，后面的卡片依次跟上，最终顺序就和数组一致。

第四步：有 pin 时，先排“座次表”再插入。 这里做的事情很像安排座位：

  • 先按位次从小到大给有 pin 的人排序；
  • 把没 pin 的人洗乱；
  • 从洗好的队列开始，一个一个把 pin 的人 splice 进指定下标。

pinned[k].pos - 1 是因为 pin: 1 表示“第一位”，而数组下标从 0 开始；Math.max(..., 0) 防止你手滑写成负数；Math.min(..., ordered.length) 防止 pin: 99 时 splice 越界——超出长度就落到末尾，不会报错。

几个实际结果，可以直接对照：

写法 结果
谁都没写 pin 纯随机，每次不同
只有 A 写 pin: 1 A 永远第一，其余人随机
A 写 pin: 1，B 写 pin: 3 A 第一，B 第三，其余人随机填空位
两张卡都写 pin: 2 后插入的那张占据第 2 位，另一张被挤到后面
写 pin: 99（只有 5 个人） 落到最后一位，不报错

link.yml 的注释里写的是“多个 pin 冲突时按数字小的在前”，指的是数字不同的情况（比如 pin: 1 和 pin: 3 会各自占住自己的位次）。如果两个人写了同一个数字，后插入的会插在前面，这是 splice 的天然行为，知道就好，不必特意去用。

4.5 为什么最后要包一层 DocumentFragment

DocumentFragment 是一个“不在页面上的临时容器”。把卡片先搬进它里面，浏览器不会为每一次移动重新计算布局；最后 group.appendChild(frag) 一次性把整批节点挂上去，只触发一轮重排。

注意这段只在“有 pin”的分支里执行；纯随机那条分支是逐个 appendChild 的。两者结果完全一样，只是后者会多触发几次重排，作者没有再去优化——先跑对，再谈性能。

读者可能感觉不到差别，但友人帐有几十张带截图的卡片，逐个插入在低端手机上会有明显的一次“跳一下”。

4.6 run()：先找根容器，再找分组

这段代码解释了三个设计决定：

  1. 为什么要从 .flink 开始找。 一篇文章里可能内嵌 flink 标签，也可能有多个 .flink 容器。以根容器为范围，脚本在任何页面都能工作，不会误伤别的地方。
  2. 为什么要读 data-shuffle。 关掉随机时不用删脚本，模板写一个 off 就行（第 6 节）。
  3. 分组选择器是 .site-card-group, .flink-list。 注意，h2 和 .flink-desc 不在这个选择器里，所以它们永远不参与洗牌。

还有一个容易忽略的细节：querySelectorAll 返回的是静态 NodeList，洗牌过程中 DOM 在变，但这个列表不会跟着变，所以循环是安全的。

4.7 启动时机：两个分支不是重复代码

  • 如果脚本在 <head> 里、或者以普通 <script> 写在很靠前的位置，执行时 DOM 还没解析完（readyState === 'loading'），必须等 DOMContentLoaded；
  • 如果是 defer 脚本、或者写在页面最底部，执行时 readyState 已经是 interactive，直接跑就行。

两个分支都写，是为了让这个文件不管被放到哪里都能用。本站用的是 defer，实际走的是 run() 那一支。

这一行单独讲，见第 7 节。

第 7 步：pjax 下为什么还留着 pjax:complete

本站开了 pjax。点击站内链接时，浏览器不会整页刷新，而是把新页面的内容取回来，替换掉 #body-wrap 这些容器。这带来一个新手很容易懵的现象：

  • 整页刷新（F5、地址栏回车）：脚本重新加载，run() 正常执行；
  • pjax 换页：document 没被替换，<script> 会不会重新执行，取决于 pjax 版本和配置。

本站的处理很朴素：脚本第一次加载时就在 document 上挂一个监听，之后每次 pjax 完成，都把 run() 再跑一遍。

为什么这样是安全的：

  1. document 不会被 pjax 替换，事件监听一直在；
  2. run() 是幂等的——它只是读当前 DOM、重新洗一遍、按新顺序放回去。跑一次和跑三次，结果都是“随机顺序”，不会有副作用；
  3. 即使某些 pjax 实现把页面里的脚本也重新执行了一遍，导致监听被挂了两次，最坏的结果也只是洗完又洗一次，页面依然正确。

对比一下，如果这段逻辑是“点一下按钮计数 +1”，重复绑定就会变成一次点击加两次，那才是真正的 bug。写 pjax 兼容代码时，先问自己：这个函数重复执行会不会叠加副作用？

第 9 步：打乱之后，本站这些功能会不会出问题

这是最值得单独讲的一节，因为友人帐页面上不只有卡片。

9.1 「N 位」角标和页脚统计照常正确

source/links/index.md 里的样式用 CSS 计数器统计数量和分类：

计数器绑定在元素上，每张卡出现一次就加一，跟它在第几个位置无关。所以顺序打乱后：

  • 「N 位」还是总人数；
  • 页脚「共 N 位朋友」还是总人数；
  • 分类数也不会变。

如果你打乱后发现角标变成 0，那不是计数器的问题，而是你把卡片 appendChild 到了分组容器外面——检查 group 变量是不是拿错了。

9.2 截图和头像不会重新下载

appendChild 移动的是已有的 DOM 节点，img 标签的 src、loading、onerror 都原样保留。浏览器看到的是同一个图片元素换了位置，不会重新发起请求。

9.3 点击、悬停、键盘 Tab 都正常

卡片是 <a> 标签，跳转靠浏览器原生行为，没有 JS 绑在卡片上。移动节点不会影响 href、target、rel，也不会影响 CSS 的 :hover。

唯一的变化是：键盘用户按 Tab 的顺序会跟着新 DOM 顺序走。也就是说每次刷新，Tab 的遍历顺序不同。对友链页面来说这不算问题，但你要知道它确实变了。

9.4 会不会“闪一下”

脚本执行到第一次绘制之间的间隔很短，正常网络下看不到。如果你那边确实明显，可以给分组容器一个最小高度，避免图片加载前后高度跳动：

9.5 两张卡片时的“没变化”是正常的

n 张卡片一共有 n! 种排列。两张时有 2 种，所以有 50% 的概率洗完看起来和原来一样；三张是 6 种，约 17% 重复。判断代码是否生效，别只看一次刷新，多刷几次或者看控制台输出。

第 10 步：照做了没反应？按这个表查

现象 最可能的原因 怎么查
刷新后顺序完全不变 脚本没加载 / 浏览器缓存 / 选择器没命中 Network 里看 js 是否 200；控制台跑 document.querySelectorAll('.site-card').length
控制台报 404 路径写错 源文件 source/js/x.js 对应页面里的 /js/x.js，src 里不要带 source/
顺序变了，分类标题也乱了 分组选择器选得太大 groups 不应该包含 h2、.flink-desc
有卡片“消失”或跑到了别的分组 用了 querySelectorAll 抓到了嵌套卡片 改成遍历 group.children
写了 pin 也不固定 模板没输出 data-pin / 用的是 flink 标签 F12 看 a.site-card 上有没有 data-pin="2"
顺序变了但页面卡一下、图片重载 用 innerHTML 重写了容器 改成 appendChild 移动节点
pjax 点进来顺序不变，F5 正常 脚本没在目标页加载 / 事件名不对 控制台看 pjax:complete 是否触发
角标变成 0 位 卡片被移出了分组容器 检查 group 是不是 .site-card-group
手机上完全没变化 缓存或浏览器“阅读模式” 换隐身窗口再试
改完代码没生效 旧版本被缓存 把 ?v= 改个数字，或 Ctrl + F5
每次刷新顺序都一样，但确实是随机的 浏览器启用了“返回缓存” 用普通刷新验证，前进后退不算
控制台报 Cannot read properties of null 页面没有 .flink，但代码在找子元素 run() 里先判断 roots.length

第 11 步：上线前检查清单

  • [ ] source/js/flink-shuffle.js 存在，且路径能被访问到；
  • [ ] <script defer src="/js/flink-shuffle.js?v=..."> 写在友链页面末尾；
  • [ ] 每次刷新（Ctrl + F5）顺序都在变；
  • [ ] 分类标题和描述没有被一起打乱；
  • [ ] 多个分组之间没有互相串卡；
  • [ ] 写了 pin 的卡片确实固定在对应位次；
  • [ ] 没写 pin 的卡片都有机会排到第一；
  • [ ] pjax 从别的页面点进友人帐，顺序也会变；
  • [ ] 「N 位」角标和页脚总数没变；
  • [ ] 截图、头像正常显示，点击能跳转；
  • [ ] 手机端刷新正常，没有明显闪动；
  • [ ] _config.chengic.yml 里 flink_shuffle: true；
  • [ ] 改过脚本后 ?v= 版本号已经更新；
  • [ ] hexo clean && hexo generate 通过，public/js/ 下有这个文件。

最后说一句

随机排序本身是个很小的功能，代码不到 100 行，但它解决的是一个挺实际的问题：友人帐不该有“永久的第一屏”和“永远的最后一位”。排序固定的时候，排在后面的朋友几乎不会被访客看到，这跟“交换友链”的初衷是相违背的。

所以如果你要抄这份代码，我的建议是：先保持所有人纯随机，pin 只留给真正需要的例外。别一上来就把自己和几个好朋友钉在前几位——那样做的页面，和没有这个功能没什么区别。

代码全部在 source/js/flink-shuffle.js，想改的人可以直接从第 3 节复制。改完记得把 ?v= 换一个版本号，不然浏览器会继续用旧文件陪你演半天“怎么没变化”。
